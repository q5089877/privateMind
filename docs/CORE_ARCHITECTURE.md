# 轉念之間目前核心架構

本文件只描述目前程式實際使用的產品核心。若未來要加入新的流程、資料保存或 AI 角色，必須先更新本文件，再開始實作。

## 一、產品定位

轉念之間讓使用者留下當下想法，並從不同經典角度重新看一眼。

核心原則：

- 使用者先說，AI 再回應。
- AI 提供看事情的角度，不替使用者做決定。
- 經典是 AI 背後的思考依據，不把使用者變成經典課程的學生。
- 每次成功回答都顯示一小句固定經文，並附白話說明；目前金剛經與道德經各有 30 句經文，由固定經文庫提供，不由模型自由改寫。
- AI 只回傳最符合原文的 `quoteId`；程式依 ID 顯示固定經文，避免 AI 自行改寫或反覆固定選同一句。
- AI 依使用者原文與所選經文產生短標題；只有成功收到 AI 標題後才顯示，載入與失敗狀態不使用寫死的替代標題。
- AI 失敗時保持空白，只提供重試，不使用預設答案冒充 AI 回應。
- 使用者可以選擇是否查看第二個角度。

## 二、目前產品流程

```text
首頁
  ↓ 使用者輸入
金剛經視角回答
  ├─ 成功：顯示白話說明與可選問題
  ├─ 失敗：只顯示「重試」
  └─ 使用者點擊「看看道德經視角」
       ↓
     道德經視角回答
       ├─ 成功：顯示白話說明與可選問題
       └─ 失敗：只顯示「重試」
```

目前不要求使用者完成任何層級、問卷或對話進度。每次新增文字會取代目前核心回答，並維持在同一個畫面中繼續對話。

## 三、使用者介面

主要畫面由 `src/App.tsx` 負責：

- 首頁：文字輸入、留下按鈕、輕按／長按定心按鈕。
- 對話畫面：顯示使用者輸入、金剛經回答、道德經回答與下一次輸入框。
- 回首頁：離開目前對話畫面，回到首頁狀態。

`src/components/CoreAnswerCard.tsx` 負責核心回答卡片：

- 顯示視角名稱。
- AI 成功時依序顯示經文、對應解說、白話說明與一個問題。
- 對應解說必須直接說明經文如何對應使用者原文，不得只是泛泛談經典。
- 只顯示 AI 依原文與經文產生的動態短標題，不顯示寫死的視角標題。
- 顯示一個可跳過的反思問題。
- AI 失敗時不顯示任何預設內容，只顯示重試按鈕。

目前沒有圖片素材依賴，也沒有五層卡片、歷史回看、備份或資料庫畫面。

## 四、兩個核心視角

兩個視角固定存在於 `src/services/ai/roles/coreAnswerRole.ts`，由 `CoreLens` 區分：

```ts
type CoreLens = 'diamond_sutra' | 'tao_te_ching';
```

### 金剛經

主要看：

- 是否把念頭當成事實。
- 是否把一次事件、角色或立場固定成全部真相。
- 是否能把當下發生的事與後來的判斷分開。
- 是否保留重新看待事情的空間。

金剛經只作為思考框架，不要求回答堆疊經典術語，也不能替使用者判定他人動機。

### 道德經

主要看：

- 事情中是否存在過度用力或控制。
- 哪些地方不必急著推動結果。
- 如何順著現況保留空間。
- 「無為」不等於放棄，也不等於要求使用者退讓。

道德經只作為思考框架，不把回答寫成教訓、命令或信仰要求。

兩個視角可以使用相同的自然詞語，不以禁止特定經典詞彙作為區分或失敗條件。差異來自觀察方向：

> 金剛經看固定認定；道德經看用力與留白。

## 五、AI 回答契約

AI 角色由 `src/services/ai/roles/coreAnswerRole.ts` 定義，前端只透過 `src/services/coreConversation.ts` 呼叫。

輸入包含：

- 使用者目前文字。
- 同一次畫面的最近對話內容。
- 指定視角：`diamond_sutra` 或 `tao_te_ching`。

輸出固定為 JSON：

```ts
interface CoreAnswer {
  lens: CoreLens;
  title: string;
  quoteId: string;
  quote: string;
  evidence: string;
  coreQuestion: string;
  answer: string;
  plainLanguage: string;
  reflectionQuestion: string;
}
```

回答規則：

- 從固定核心問題中選擇一個切入點。
- `answer` 是對應解說，目標約 45–140 個中文字。
- 不使用 Markdown 標題或長篇清單。
- `plainLanguage` 目標約 25–70 個中文字，且不得與 `answer` 完全重複。
- `answer` 必須說明本視角如何套用到使用者原文，不得只是延長白話說明。
- 回答附帶目前文字或同次對話前文中的 4–24 字證據片段，並由程式驗證其確實存在；英文字母比對不區分大小寫。
- Schema 會依目前視角限制 `lens` 與 `quoteId`，並將 `coreQuestion` 限定為固定問題清單。
- 輸出額度保留足夠空間給思考型模型完成 JSON，避免思考內容吃掉回答額度。
- 只提出一個可跳過的反思問題。
- 不診斷、不預言、不命令、不替使用者下結論。
- 不把猜測寫成確定事實。
- 不直接替使用者回答反思問題。

## 六、驗證與失敗處理

AI 回傳必須通過 `coreAnswerRole.read()` 的基本驗證：

- JSON 可解析。
- `lens` 與目前要求的視角一致。
- `coreQuestion` 必須來自固定核心問題。
- `answer`、`plainLanguage` 與 `reflectionQuestion` 不得為空，且符合長度限制。
- 反思問題只能包含一個問號。
- `evidence` 必須逐字存在於使用者目前輸入中。
- 不得包含診斷、命令、預言或固定人格判斷。
- `readResult()` 直接接收完整 `CoreAnswerSource`，自行合併目前文字與同次對話前文並保留結構化失敗原因；對外的 `read()` 仍回傳 `null`，維持現有服務介面相容。

服務失敗、網路錯誤、模型格式錯誤或驗證失敗時，`getCoreAnswer()` 回傳 `null`。前端以失敗狀態呈現「重試」按鈕，不使用固定文字代替 AI 回答。

重試會重新使用目前最後一則使用者文字呼叫同一個視角，不會新增假的回答或改寫使用者原文。

## 七、資料與服務邊界

- `App.tsx`：管理目前畫面狀態與使用者操作。
- `CoreAnswerCard.tsx`：只負責回答卡片呈現與展開／收合。
- `coreConversation.ts`：負責呼叫 Worker 與處理成功／失敗結果。
- `coreAnswerRole.ts`：負責兩個視角的 Prompt、輸出格式與 Validator。
- `shared.ts`：提供模型名稱、傳輸型別與 JSON 正規化工具。
- `cloudflare/worker.js`：只負責將前端請求安全轉送至 Gemini，不包含產品 UI 或經典判斷。

目前產品不建立或維護：

- 五層冰山流程。
- IndexedDB 或 Firestore 使用者資料保存。
- Session、Review、Backup、Landing、Explore。
- 多視角選單或五種經典選擇器。
- AI 產生的歷史洞見或跨時間分析。

## 八、修改檢查

任何後續變更都必須確認：

1. 是否仍維持金剛經先回答、道德經由使用者主動查看？
2. 是否仍只有一個主要回答焦點？
3. AI 失敗時是否保持空白並提供重試？
4. 是否避免把經典術語變成說教內容？
5. 是否沒有替使用者做決定或製造新的流程負擔？
